ShoppingOnline

An e-commerce platform on a .NET 10 API and Next.js 16 storefront: user accounts, a vendor-backed product catalog, FIFO inventory fed by purchase orders, saved shipping addresses, and tax-inclusive order processing — plus an admin back office for the whole thing.

.NET 10 · ASP.NET Core EF Core · PostgreSQL Next.js 16 · React 19 Autofac · Mapster · Paseto .NET Aspire orchestration
01 — Overview

What the system does

Two audiences share one platform: customers shopping a storefront, and admins running the back office behind it — same database, same domain rules, different surface.

Storefront

Customer shopping

Browse the catalog by category, place orders against a saved address, track order status, manage a profile.

Back office

Admin operations

Manage products, categories and vendors; issue and receive purchase orders; view read-only stock; activate or deactivate user accounts.

Engine

FIFO inventory

Stock is a ledger of received lots. Orders draw down the oldest lot first, atomically, across whichever vendor supplied it.

02 — Architecture

Layered solution structure

A conventional four-layer backend (API → Handler → Service → Database/Model) plus two supporting apps: an Aspire AppHost for local orchestration and a Next.js frontend.

ShoppingOnline.API
ASP.NET Core controllers, versioned routes under /api/*, Swagger, entry point.
ShoppingOnline.Handler
One handler interface per use case (CQRS-style) — e.g. ICreateOrderHandler, IReceivePurchaseOrderHandler.
ShoppingOnline.Service
Domain services per aggregate (Orders, Products, Stocks, Vendors, Purchase Orders, …) holding the business rules.
ShoppingOnline.Database
EF Core ShoppingDbContext, table configs, migrations, unit of work.
ShoppingOnline.Model
Entities, DTOs, request/response contracts shared across layers.
Component.Abstractions / Data
Cross-cutting: Paseto auth, encryption, email, health checks, base DbContext/UoW.
AppHost + Frontend
.NET Aspire orchestrates Postgres + API + web; Next.js 16 / React 19 / Tailwind v4 storefront and /admin.
03 — Sales & Inventory Flow

How a product goes from vendor to customer

The order in which these actually happen — inventory is filled before it can be sold, and every price or address is frozen the moment it's used.

Admin creates a Purchase Order

Drafted against one vendor with quoted quantities and reference costs.

PO is sent

Status moves to Sent; an email goes to the vendor's contact.

Stock is received

Admin records what actually arrived — partial or multiple receipts per PO are supported. Each receipt creates a new dated Stock lot at its real cost.

Customer places an order

Buys a product and quantity — never a vendor or lot directly. A saved shipping address is required.

FIFO allocation fulfills the line

Oldest lot first across all vendors, with an atomic conditional decrement per lot so two customers can never oversell the same units.

Price, tax and address are snapshotted

Product.SellPrice / TaxRatePercent and the address text are copied onto the order — later catalog or address edits never rewrite history.

Confirmation email is sent

Customer receives confirmation; the order enters the Pending → Confirmed → Shipped → Delivered lifecycle (or Cancelled).

04 — Cart Mechanism

A client-side cart, priced for real only at checkout

The cart never touches the backend until checkout. It's a React context (CartProvider) backed by localStorage — nothing the server needs to know about, or trust, before then.

Storage

localStorage, not the server

Cart state lives entirely in the browser under the shopping-cart key, hydrated in a post-mount effect to avoid an SSR hydration mismatch — it survives a page refresh but not a different device or browser.

Contents

Product, price snapshot, quantity

Each line tracks product_id, product_name, price and quantity; adding the same product twice merges into the existing line instead of duplicating it.

Checkout

Only product_id and quantity are sent

The client-held price is display-only — the order request sends just product_id/quantity per line, and the server recomputes the real price and tax from Product.SellPrice/TaxRatePercent (see Sales Flow), so a stale or tampered client price can never reach an order.

Lifecycle

Cleared only after a successful order

The cart is cleared and the browser redirected to the new order's detail page only once the order request succeeds; a failed submission leaves the cart untouched so the customer can retry.

05 — Order Lifecycle

What the Status enum actually does today

Only two transitions exist in the current code: an order is created as Pending, and it can be cancelled — while still Pending — back to Cancelled. Confirmed, Shipped and Delivered are declared on the enum but no handler, service or endpoint ever assigns them yet.

08 — Frontend Page & Route Overview

Storefront and admin pages, and who can reach them

The Next.js app has three access tiers, enforced in two places: proxy.ts middleware gates whole route prefixes on a session cookie being present, and admin/layout.tsx additionally checks the signed-in profile's role server-side.

Tier 1

Public pages

No gate at all — catalog browsing and auth pages are open to anyone.

Tier 2

Session-gated

proxy.ts redirects to /sign-in?next=... when session_token is missing — it only checks the cookie is present, not that the token still validates.

Tier 3

Admin-gated

Everything under /admin additionally requires profile.role === "Admin", checked in admin/layout.tsx; anyone else is redirected to /.

Forced redirect

Must-change-password

If the must_change_password cookie is set, every navigation is redirected to /change-password until it's cleared.

12 — Deployment & Operations

How it runs locally

Orchestrated end-to-end by the Aspire AppHost — no manual container or migration steps.

Orchestration

.NET Aspire AppHost

Wires up a Postgres resource (shoppingDb), the API project (shoppingonline-api) referencing it, and the Next.js frontend (shoppingonline-frontend) referencing the API — one dotnet run starts all three.

Health & docs

/health and /docs

A health-check endpoint is mapped at /health; API documentation is served by Scalar at /docs, backed by the OpenAPI document. Both are development-only.

Configuration

Minimal committed settings

appsettings.json commits only AllowedHosts — connection strings, Paseto keys and email/SMTP settings are supplied by Aspire/environment at run time, not checked into source.

Migrations

Applied automatically

EF Core migrations run on startup, and a seeded admin account plus demo catalog are created on first run (see README).

13 — Known Limitations

What isn't built yet

Observed gaps in the current code — not a roadmap, just what's actually missing today.

Not implemented

No payment or refund flow

No payment-related file exists anywhere in the codebase, and OrderStatus has no Refunded or Returned state.

Not implemented

Fulfillment tracking stops at Cancelled

Confirmed, Shipped and Delivered exist as enum values but no admin endpoint or handler ever sets them — see Order Lifecycle.

Not implemented

No product reviews or ratings

No review or rating entity, table, or controller exists in the model or API.

Basic only

Catalog search is simple filtering

GetProductsRequest filters by search text, category, vendor and active status with paging — there's no full-text search engine behind it.
